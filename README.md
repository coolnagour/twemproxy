# twemproxy (nutcracker) with zone-aware Redis routing

## What's different from the original twemproxy?

This fork adds zone-aware read routing for Redis in cloud setups (AWS, GCP, Azure). The idea is simple: when you have read replicas spread across availability zones, send most of your reads to the replica in the same zone as the proxy. That cuts latency and avoids cross-AZ data transfer charges.

It does this without you having to label zones or set thresholds. The proxy measures the real connection latency to each replica and works out which ones are close.

What it adds on top of stock twemproxy:

- Zone-aware routing. Most reads go to the same-AZ replica, with a configurable percentage so you still spread some load.
- Replica discovery from a single reader endpoint. The proxy re-resolves the DNS name on an interval and keeps every IP it sees, so it learns the whole replica set over time.
- Latency measurement. It tracks the connection latency per replica and prefers the faster ones, which keeps it pointed at the same zone and backs off nodes under pressure.
- Failover. It handles a replica going away or a DNS record changing without a restart.

## docker-compose.yml example

```
version: '3.3'

services:
  twemproxy:
    image: bobbymaher/twemproxy:2.1.1
    ports:
      - "6378:6378"  # Redis read port
      - "6379:6379"  # Redis write port
      - "22222:22222" # Stats port
    environment:
      # Redis endpoints. Point READ_HOST at your reader endpoint so the proxy
      # can discover the replicas behind it.
      READ_HOST: "redis-ro.cc.ng.0001.euw1.cache.amazonaws.com:6379"
      WRITE_HOST: "redis.cc.ng.0001.euw1.cache.amazonaws.com:6379"

      # Zone-aware routing
      ZONE_WEIGHT: "95"                   # 95% of reads to the same-AZ replica
      DNS_RESOLVE_INTERVAL: "30"          # re-resolve DNS every 30 seconds
      DNS_EXPIRATION_MINUTES: "5"         # keep an IP for 5 min after it stops showing up in DNS
      DNS_HEALTH_CHECK_INTERVAL: "30"     # health check every 30 seconds
    volumes:
      - ./logs:/var/log/twemproxy # logrotate this
    networks:
      - redis-network
    restart: unless-stopped


networks:
  redis-network:
    driver: bridge

volumes:
  logs:
```

The read pool generated by the container is set up for dynamic discovery automatically, so pointing `READ_HOST` at a reader endpoint is enough.

View your connected nodes and their traffic:

```
curl -s http://localhost:22222 | jq '.[0].pools.redis_read.servers[].dns_hosts.address_details[] | {cname, latency_us, healthy, current, requests}'
```

## Docker quick start

### Using docker compose (recommended)

1. Clone and build:
```bash
git clone https://github.com/coolnagour/twemproxy.git
cd twemproxy
```

2. Copy the example configuration:
```bash
cp docker-compose.example.yml docker-compose.yml
```

3. Set your Redis endpoints:
```yaml
# docker-compose.yml
services:
  twemproxy:
    environment:
      READ_HOST: "your-redis-ro.cache.amazonaws.com:6379"
      WRITE_HOST: "your-redis-primary.cache.amazonaws.com:6379"
      ZONE_WEIGHT: "95"  # 95% of reads to the same-AZ replica
```

4. Start it:
```bash
docker-compose up -d
```

5. Check status and stats:
```bash
# logs
docker-compose logs twemproxy

# stats
curl http://localhost:22222

# test the pools
redis-cli -p 6378 ping  # read pool
redis-cli -p 6379 ping  # write pool
```

## Configuration reference

### Zone-aware routing

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `zone_aware` | boolean | `false` | Enable zone detection and routing for this pool |
| `dynamic_endpoint` | boolean | `false` | Treat this pool's server as a DNS name to re-resolve and accumulate addresses from (a reader endpoint). Required for replica discovery. |
| `zone_weight` | integer | `25` | Percent of reads sent to a same-zone replica (0-100) |
| `dns_resolve_interval` | integer | `30` | DNS re-resolution interval (seconds) |

`dynamic_endpoint` is an explicit opt-in. Earlier versions guessed it from a `-ro` in the hostname, which was a foot-gun: a write pool whose name happened to contain "ro" could quietly start round-robining writes across read replicas on a failover. Now you turn it on per pool, so the write pool stays pinned to the primary.

### Connection management

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `connection_pooling` | boolean | `false` | Enable connection pooling |
| `connection_warming` | integer | `0` | Number of connections to pre-warm |
| `connection_idle_timeout` | integer | `300` | Close idle connections after N seconds |

### Health and monitoring

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `dns_failure_threshold` | integer | `3` | Failures before marking a server unhealthy |
| `dns_cache_negative_ttl` | integer | `30` | Negative DNS cache TTL (seconds) |

### Security and encryption

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `tls_enabled` | boolean | `false` | Enable TLS |
| `tls_verify_peer` | boolean | `true` | Verify TLS peer certificates |

## Zone weight examples

Cost first, minimal cross-AZ traffic:
```yaml
zone_aware: true
dynamic_endpoint: true
zone_weight: 99    # 99% same-AZ, 1% cross-AZ
```

Balanced between cost and load spread:
```yaml
zone_aware: true
dynamic_endpoint: true
zone_weight: 70    # 70% same-AZ, 30% spread across the rest
```

More cross-AZ utilisation:
```yaml
zone_aware: true
dynamic_endpoint: true
zone_weight: 40    # 40% same-AZ, 60% spread
```

## How zone detection works

1. Discovery. The proxy resolves the DNS name to find all the server IPs.
2. Latency. It measures the actual connection latency to each one.
3. Grouping. It splits them by latency: anything at or below (min + 25% of the range) is treated as same zone, the rest as cross zone.
4. Routing. It sends the configured percentage of reads to the same-zone group.
5. Re-check. It re-runs the zone analysis every 2 minutes.

You do not set zone IDs or latency thresholds. It adapts to whatever infrastructure it is running on, so it works the same on AWS, GCP, Azure, or anywhere else.

---

## Failover

zone_weight is a preference, not a hard pin. The proxy only sends reads to a same-zone replica when there is a healthy one. If a whole zone goes down, its replicas get marked unhealthy and drop out of the pool, so reads move to a healthy replica in another zone on their own. Even at zone_weight: 100 you keep serving reads as long as any zone is up. It only runs out of road when every replica in every zone is unhealthy.

Two things worth knowing if you set it to 100:

- It is never literally 100%. About 5% of reads go to a random healthy replica, cross-zone included, to keep the latency numbers fresh so the failover targets stay known good.
- Failover is health driven, and health comes from real request failures. So when a zone drops there is a short window where some reads hit the failing replicas and retry before they get excluded. Set server_failure_limit: 1 and a short server_retry_timeout for fast failover.

## Traditional configuration

All the original twemproxy options still work:

```yaml
pools:
    example:
        listen: 127.0.0.1:22121

        distribution: ketama
        auto_eject_hosts: true
        redis: true
```

### Core options

+ **listen**: the listening address and port (name:port or ip:port) for this server pool
+ **redis**: speak the redis protocol. Defaults to false.
+ **hash**: hash function (one_at_a_time, md5, crc16, crc32, fnv1_64, fnv1a_64, etc.)
+ **distribution**: key distribution mode (ketama, modula, random)
+ **timeout**: server connection timeout in msec
+ **auto_eject_hosts**: temporarily eject failed servers
+ **server_retry_timeout**: time before retrying an ejected server (msec)
+ **server_failure_limit**: failures before a server is ejected
+ **servers**: list of address, port and weight (name:port:weight or ip:port:weight)

## Health checks and recovery

### How health monitoring works

twemproxy uses passive health monitoring. It does not send active PING commands or probes. Health is worked out from real client request failures and successes.

- Successful request: `server_ok()`, reset the failure count to 0
- Failed request: `server_failure()`, increment the failure count
- Server ejected: when failures exceed `server_failure_limit`
- Automatic retry: after `server_retry_timeout`

### Recovery example

When a Redis server reboots or fails for a bit:

1. Detection. Requests to it start failing, the failure count climbs, and it gets ejected once it passes `server_failure_limit`.
2. Ejection. It is out of rotation for `server_retry_timeout`, with no traffic sent to it.
3. Recovery. After the timeout the proxy retries it. The first success resets the failure count and it is back in rotation.

### Configuration example

```yaml
pools:
    read:
        server_retry_timeout: 10000    # retry a failed server after 10 seconds
        server_failure_limit: 1        # eject after 1 failure
        auto_eject_hosts: true
```

With this, a rebooted server is out of rotation for about 10 seconds, then rejoins once it is healthy.

### Recovery with dynamic DNS

With accumulative DNS resolution (`dns_expiration_minutes`), recovery is more forgiving:

- IP addresses stay in the list during an outage instead of being dropped immediately.
- Health is tracked per IP.
- An IP is only removed once it is both unhealthy and no longer showing up in DNS.
- A healthy server resumes taking traffic straight away.

### Health check options

| Option | Default | Description |
|--------|---------|-------------|
| `auto_eject_hosts` | `false` | Enable automatic ejection and recovery |
| `server_failure_limit` | `2` | Failures before ejecting a server |
| `server_retry_timeout` | `30000` | Milliseconds before retrying an ejected server |
| `dns_expiration_minutes` | `5` | Minutes to keep an IP not seen in DNS (if healthy) |
| `dns_health_check_interval` | `30` | Seconds between health analysis cycles |

For fast failover, set `server_failure_limit: 1` and `server_retry_timeout: 10000`.

## Changes on top of the original twemproxy

### Config reload

Send SIGHUP to reload the config at runtime:

```
sudo pkill -1 nutcracker
```

Reload works in multi-process mode (`worker_processes` greater than 0): the master re-reads the config and recycles the workers. In single-process mode (`worker_processes: 0`) there are no workers to recycle, so SIGHUP just logs a line telling you to restart to apply config changes.

### Reader endpoints and replica discovery

If you are on AWS with a read only endpoint (the hostname usually contains `-ro`), set `dynamic_endpoint: true` on that pool.

The reader endpoint sits behind round robin DNS with a short TTL, about 15 seconds. If you list it once, the proxy resolves it to a single IP at startup and every read hits the same replica. If you list it many times hoping to hit them all, you often get the same IP back, so the load still does not spread.

With `dynamic_endpoint: true` the proxy re-resolves the name every `dns_resolve_interval` seconds and keeps every IP it sees (it ages one out after `dns_expiration_minutes` once it stops appearing). Over a minute or so it learns the full replica set behind the endpoint and spreads reads across them, then zone-aware routing prefers the closest one. You do not need an external script to rewrite the config.

# twemproxy (nutcracker) [![Build Status](https://secure.travis-ci.org/twitter/twemproxy.png)](http://travis-ci.org/twitter/twemproxy)

twemproxy is a multi-process, fast and lightweight proxy for [memcached](http://www.memcached.org/) and [redis](http://redis.io/) protocol.
It was built primarily to reduce the number of connections to the caching servers on the backend.
This, together with protocol pipelining and sharding enables you to horizontally scale your distributed caching architecture.

This is a fork of `twitter/twemproxy` (by way of the bitleak/Meitu fork) that adds multi-process and hot-reload. Development happens on the `develop` branch, so master can track upstream changes and backporting.

The `develop` branch is stable. It has run in production at Meitu Inc. for over a year.

## Build

To build twemproxy from a distribution tarball:

    $ ./configure
    $ make
    $ sudo make install

To build in debug mode:

    $ CFLAGS="-ggdb3 -O0" ./configure --enable-debug=full
    $ make
    $ sudo make install

To build from source with debug logs and assertions enabled:

    $ git clone git@github.com:coolnagour/twemproxy.git
    $ cd twemproxy
    $ autoreconf -fvi
    $ ./configure --enable-debug=full
    $ make
    $ src/nutcracker -h

A quick checklist:

+ Use a newer version of gcc (older versions have problems)
+ Use CFLAGS="-O1" ./configure && make
+ Use CFLAGS="-O3 -fno-strict-aliasing" ./configure && make
+ `autoreconf -fvi && ./configure` needs `automake` and `libtool` installed

## Features

* Supports a master-worker process model (new)
* Supports config reload at runtime (new)
* Supports read/write split for a redis master-slave setup (new)

+ Fast.
+ Lightweight.
+ Maintains persistent server connections.
+ Keeps the connection count on the backend caching servers low.
+ Enables pipelining of requests and responses.
+ Supports proxying to multiple servers.
+ Supports multiple server pools at once.

## Zero copy

In twemproxy, all the memory for incoming requests and outgoing responses is allocated in mbuf. Mbuf enables zero-copy because the same buffer on which a request was received from the client is used for forwarding it to the server. Similarly the same mbuf on which a response was received from the server is used for forwarding it to the client.

Memory for mbufs is managed using a reuse pool. Once an mbuf is allocated it is not deallocated, just put back into the pool. By default each mbuf chunk is 16K. There is a trade-off between mbuf size and the number of concurrent connections twemproxy can support. A large mbuf size reduces the number of read syscalls, but every active connection uses up 16K of buffer, which adds up with a large number of concurrent client connections. When you need to handle a lot of concurrent client connections, set the chunk size to a smaller value like 512 bytes with the -m or --mbuf-size=N argument.

## Configuration

twemproxy is configured through a YAML file passed with the -c or --conf-file argument on start. The file specifies the server pools and the servers in each pool. It understands the following keys:

+ **listen**: the listening address and port (name:port or ip:port) or an absolute path to a sock file (e.g. /var/run/nutcracker.sock) for this server pool.
+ **client_connections**: the maximum number of client connections allowed. Unlimited by default, though OS limits still apply.
+ **hash**: the hash function. One of:
 + one_at_a_time
 + md5
 + crc16
 + crc32 (compatible with [libmemcached](http://libmemcached.org/))
 + crc32a (correct crc32 per the spec)
 + fnv1_64
 + fnv1a_64
 + fnv1_32
 + fnv1a_32
 + hsieh
 + murmur
 + jenkins
+ **hash_tag**: a two character string that marks the part of the key used for hashing, e.g. "{}" or "$$". [Hash tags](notes/recommendation.md#hash-tags) let you map different keys to the same server when the tagged part matches.
+ **distribution**: the key distribution mode. One of:
 + ketama
 + modula
 + random
+ **timeout**: the timeout in msec to establish a connection or wait for a response. By default it waits indefinitely.
+ **backlog**: the TCP backlog. Defaults to 512.
+ **preconnect**: connect to all servers in the pool on start. Defaults to false.
+ **redis**: speak the redis protocol rather than memcached. Defaults to false.
+ **redis_auth**: authenticate to the Redis server on connect.
+ **redis_db**: the DB number to use on the pool servers. Defaults to 0. twemproxy always presents itself to clients as DB 0.
+ **server_connections**: the maximum connections per server. Defaults to 1.
+ **auto_eject_hosts**: temporarily eject a server when it fails server_failure_limit times in a row. See [liveness](notes/recommendation.md#liveness). Defaults to false.
+ **server_retry_timeout**: msec to wait before retrying an ejected server, when auto_eject_hosts is true. Defaults to 30000.
+ **server_failure_limit**: consecutive failures before a server is ejected, when auto_eject_hosts is true. Defaults to 2.
+ **servers**: a list of address, port and weight (name:port:weight or ip:port:weight) for this pool.

The configuration file in [conf/nutcracker.yml](conf/nutcracker.yml) shows a working example. Use the -t or --test-conf argument to check a config file for syntax errors:

## Observability

Observability in twemproxy is through logs and stats.

twemproxy exposes stats per server pool and per server on the stats monitoring port. Stats are JSON key-value pairs, with the keys being counter names. By default stats are on port 22222 and aggregated every 30 seconds. Both are configurable on start with -c/--conf-file and -i/--stats-interval. Print the description of all stats with -D or --describe-stats:

    $ nutcracker --describe-stats

    pool stats:
      client_eof          "# eof on client connections"
      client_err          "# errors on client connections"
      client_connections  "# active client connections"
      server_ejects       "# times backend server was ejected"
      forward_error       "# times we encountered a forwarding error"
      fragments           "# fragments created from a multi-vector request"

    server stats:
      server_eof          "# eof on server connections"
      server_err          "# errors on server connections"
      server_timedout     "# timeouts on server connections"
      server_connections  "# active server connections"
      requests            "# requests"
      request_bytes       "total request bytes"
      responses           "# responses"
      response_bytes      "total response bytes"
      in_queue            "# requests in incoming queue"
      in_queue_bytes      "current request bytes in incoming queue"
      out_queue           "# requests in outgoing queue"
      out_queue_bytes     "current request bytes in outgoing queue"

Logging is only available when twemproxy is built with logging enabled. By default logs go to stderr. Use -o or --output to write to a file. On a running twemproxy you can turn log levels up and down with SIGTTIN and SIGTTOU, and reopen the log file with SIGHUP.

## Pipelining

twemproxy proxies multiple client connections onto one or a few server connections. That makes it good at pipelining requests and responses, which saves on round trip time.

For example, if twemproxy is proxying three client connections onto a single server and gets 'get key\r\n', 'set key 0 0 3\r\nval\r\n' and 'delete key\r\n' on those connections, it batches them and sends them as a single message: 'get key\r\nset key 0 0 3\r\nval\r\ndelete key\r\n'.

Pipelining is why twemproxy ends up better on throughput even though it adds a hop between client and server.
